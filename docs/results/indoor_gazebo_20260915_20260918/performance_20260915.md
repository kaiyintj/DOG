# Small House 仿真性能基线

用途：区分 Gazebo、RViz、语义处理与 Nav2 的进程负载，记录墙钟与仿真时间之比。本次未取得导航终态。

配置：indoor7 / Small House；先 navigation_enabled=false，gui=true，rviz=true；手动建图后停止键盘，在同一地图启动 Nav2 和主动感知。配置副本在 protocol/，实际启动参数以 launch 日志为准。运行前不调速、不改分辨率、不关闭障碍检查。

过程：启动前基线约 20 秒；启动加载单独标记；初始化完成静止 60 秒；键盘建图 2–3 分钟；松开控制并停止键盘，静止 60 秒；启动 Nav2，准备完成后 chair 查询，记录到终态或明显复现卡顿。所有时长为墙钟时间。

记录：processes.csv 为采样区间进程 CPU（单核 100%）、RSS、线程和相关模块命令；system.csv 为整机资源、写盘速率、接收 /clock 推算的实时率、里程计和最新速度；gpu.csv 为整卡负载；events.jsonl 为目标与桥状态；phases.tsv 为人为阶段标签。新进程第一样本用于建立基线。速度列是最近接收值，不是持续新鲜度保证。跨阶段的首个采样区间混合了两个阶段，应排除。

不订阅图像、全量点云或 posterior，不录 sensor bag。进程占用不能区分同一 GA-BSVM 进程内投影、融合和发布的函数耗时；需要根据首轮结果再做定向分析。整卡 GPU 负载不能单独归因于某个节点。RTF 是订阅端估计，严重调度延迟时结合 clock_age 和日志判断。

### 结论与边界

- Gazebo 与 GA-BSVM 是最主要的 CPU 热点；整机多核平均未满载，并不排除串行线程成为关键路径。仅凭进程统计不能确认某个线程或函数是根因。
- 实际加载的 Small House world 设置 max_step_size=0.001、real_time_update_rate=1000、real_time_factor=1；文件没有要求半速运行。未采集运行时 physics service 参数，不能排除运行中修改。
- 建图前 20 个有效样本 GA-BSVM 平均约 50.1%，后 20 个约 85.4%。负担随建图过程增加，与全图遍历开销假设一致；无地图体素计数/函数耗时，尚不能证明其因果。
- 两次 stationary 标记均仅约 7 秒，没有达到计划的 60 秒，只能作短时旁证，不作为稳定静止对照。没有 lag 标记，不能把某个样本直接对应为用户主观卡顿时刻。
- navigation 标记阶段 RTF 最低约 0.030，里程计接收年龄最高约 1.26 秒，支持存在严重短时停顿；接收器本身调度延迟也会影响这些数值。
- mapping.log 中出现 217 次历史 TF 未到达、30 次 IMU 无对齐样本；navigation.log 中出现 27 次 TF 缓存时间戳丢消息、27 次 BT tick 超时、4 次 entropy 新鲜度警告、2 次速度 watchdog 置零（统计包含启动到终止的全部日志）。不能把所有警告都归因于 CPU，时间戳与时钟配置仍需单独区分。
- 导航标记阶段最近命令采样均值：/cmd_vel 0.186 m/s，/cmd_vel_champ 0.058 m/s，speed_scale 0.311。它们是低频采到的最新命令，不是实际底盘速度，也不能捕获所有短暂置零。仿真慢和主动减速叠加解释部分观感，不能据此推导真实行走速度。
- 本次 chair 查询被接收，发布 target=(-4.978,3.273)、goal=(-4.850,2.250)，Nav2 ACCEPTED。实际导航从 chair_query 阶段已开始，navigation 标记晚约 27 秒。反馈 distance_remaining 从约 1.571 m 降至 0.474 m；日志中没有 SUCCEEDED/ABORTED/CANCELED 终态，不能记作导航成功，也不能记作超时失败。

### 下一步

1. 优先对 GA-BSVM 的投影/密度、体素更新、全图可视化与打包、熵、代价图分别测耗时，确定主要耗时再改；先处理展示生成和重复计算，保留算法输入/导航安全语义。
2. 对 Gazebo 做单变量对照：先仅关闭 gzclient，其他启动配置与轨迹不变；必要时再测 RViz。不能把关闭 GUI 等同于停止相机传感器渲染，gzserver 内物理与传感器开销仍需检查。
3. 熵已发生过期，不能简单降低供主动感知使用的熵发布频率，也不应通过放宽新鲜度或关闭 watchdog 掩盖延迟。
4. 不优先更换 SegFormer 模型、不以持久 Object ID 为性能修复；当前查询前已持续高负载。

本轮仅分析并补全本批记录，未修改算法/配置，未重跑仿真，未宣称性能已改善。
